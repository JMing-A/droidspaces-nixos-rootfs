# 架构说明

本文面向**二次开发者**：如果你要改流水线、加变体、排查构建失败，或者想把这套机制搬到别的发行版上，看这一份。

面向普通用户的下载/导入步骤见 [`使用指南.md`](使用指南.md)。

---

## 1. 总体结构

```text
输入层        variants.json         变体表（构建什么）
             systems.json          架构表（在哪构建）
             ↑
             │ 读取
驱动层        scripts/plan_build.py    输入 -> matrix
             scripts/gen_rootfs_json.py  资产 -> 索引 / 校验表
             scripts/write_notes.py      索引 -> Release notes
             ↑
             │ 调用
执行层        .github/workflows/build-nixos-rootfs.yml
             ├─ job plan
             ├─ job build   （矩阵，每格一个 runner）
             └─ job release
             ↑
             │ nix build
求值/构建     flake.nix + nix/*.nix
             输出 legacyPackages.<system>.nixosRootfsTarballs.<variant>
```

核心思想：**数据和执行分离**。变体是数据（JSON），流水线是执行，把变体加进去不需要动 YAML；反过来改 YAML 不会影响变体定义。

## 2. 三个 job 的职责边界

### 2.1 `plan`

| 项 | 内容 |
|---|---|
| 运行环境 | `ubuntu-latest`，单 job |
| 耗时 | 数十秒 |
| 输入 | 7 个 `workflow_dispatch` 输入 |
| 输出 | `tag` / `build_date` / `flake_base` / `matrix` / `job_count` / `variant_count` / `system_count` |
| 是否碰网络 | 只 `actions/checkout`，不下载 Nix |
| 失败影响 | 全流程终止，不启动任何 build |

做的事：

1. `python3 scripts/gen_rootfs_json.py --lint` —— 校验 `variants.json` / `systems.json`：必填字段、`id` 与 `file` 唯一、`experimental` 为布尔、每个 system 有 `arch` 和 `runner`。
2. `python3 scripts/plan_build.py` —— 解析输入：
   - `tag` 为空时取 `v%Y%m%d-%H%M%S`（UTC）；非 `v` 开头自动补 `v`；用正则 `v[A-Za-z0-9][A-Za-z0-9._-]*` 拒绝不安全字符；
   - `build_date` 从 tag 里 `v` 后第一段取 8 位数字，取不到就用当天 UTC 日期（这是 Droidspaces App 期望的文件名形状）；
   - `include_experimental=false` 时先过滤掉 `experimental: true` 的变体；
   - `variants` / `systems` 支持 `all` 或逗号分隔，未知取值直接 `fail` 并打印可用值；
   - `flake_ref` 为 `main` 或空时不追加 ref（`github:owner/repo` 本身就默认分支），否则拼成 `github:owner/repo/<ref>`。
3. 把结果以 `key=value` 形式写进 `$GITHUB_OUTPUT`，其中 `matrix` 是一行紧凑 JSON，供 `build` 用 `fromJSON()` 直接吃。

**边界**：`plan` 不做任何构建、不改仓库、不碰 Release。它唯一的副作用是写出 workflow outputs 和 step summary。

### 2.2 `build`

| 项 | 内容 |
|---|---|
| 运行环境 | `matrix.runner`（来自 `systems.json`），`aarch64-linux` 用 `ubuntu-24.04-arm`，`x86_64-linux` 用 `ubuntu-latest` |
| 实例数 | `变体数 × 架构数` |
| 超时 | `timeout-minutes: 350` |
| 失败策略 | `fail-fast: false` |
| 产出 | `dist/*.tar.xz` + `dist/SHA256SUMS-*.txt`，作为 Actions artifact（保留 7 天） |

每个格子的步骤固定：

| 步骤 | 说明 |
|---|---|
| `actions/checkout@v5` | 取到 `variants.json` / `systems.json`（缓存 key 里要哈希它们） |
| 安装 Nix | `DeterminateSystems/nix-installer-action@v23`，Determinate Nix 默认带 flakes，省掉 `experimental-features` 配置 |
| 还原 `/nix` | `nix-community/cache-nix-action@v6`，见 §5 |
| `nix build` | `nix build <flake_base>#<attr_path> --out-link ./result`，带 `--keep-going --print-build-logs --accept-flake-config` |
| 收集产物 | `mkdir -p dist` → `find -L ./result -type f -name '*.tar.xz'` → 必须恰好 1 个 → `mv` 成规范名 → `chmod 0644` → `sha256sum` 写 `SHA256SUMS-<arch>-<file>.txt` |
| 上传 artifact | `actions/upload-artifact@v4`，名字 `rootfs-<arch>-<variant_id>`，`if-no-files-found: error` |

**边界**：`build` 不创建 Release、不提交仓库、不碰 `rootfs.json`。它只对「我的这个格子」负责。

#### 2.2.1 为什么必须是 `find -L`

`nix build --out-link ./result` 创建的是软链：

```text
result -> /nix/store/<hash>-nixos-system-.../
```

`find ./result -type f` 在软链起点上默认不跟随，因此遍历不到任何普通文件，结果是 `found 0`，job 报 `expected exactly one .tar.xz under ./result, found 0`。

这是**第一阶段流水线的真实 bug**：构建实际成功，收集步骤错杀。修正方式有两种，本项目选了前者：

| 方案 | 写法 | 评价 |
|---|---|---|
| 跟随软链（已采用） | `find -L ./result -type f -name '*.tar.xz'` | 改动最小，保留 `--out-link ./result` |
| 用 store 路径 | `nix build --print-out-paths` 拿到路径后再 `find` | 更严谨，但要改命令结构 |

同时保留一条调试输出：数量不对时打印 `find ./result -maxdepth 3 -type f | head -50`，方便下次一眼看出产物结构。

#### 2.2.2 为什么 `fail-fast: false`

一个变体在求值阶段挂掉（例如 systemd 版本与 nixpkgs 不匹配），不代表其他变体也坏。并行矩阵用 `false` 的好处：

- 一次 run 就能看到**所有**格子的状态，不用逐个重跑；
- 不会因为第一个失败就取消后续，浪费已付出的缓存下载。

代价是 `release` 仍然 `needs: [plan, build]`，所以**任何一格失败都会阻止发布**。要发布健康变体，用更窄的 `variants` 重跑一次。

### 2.3 `release`

| 项 | 内容 |
|---|---|
| 运行环境 | `ubuntu-latest`，单 job |
| 前置条件 | `needs: [plan, build]` 且 `inputs.publish` 为真 |
| 权限 | `contents: write`（创建 Release + 推送提交） |
| 产出 | GitHub Release（含全部 tarball 与 `SHA256SUMS-*.txt`）+ 更新后的 `rootfs.json` |

步骤：

1. checkout 默认分支，`fetch-depth: 0`（后面要 rebase 推送）。
2. `actions/download-artifact@v4`，`pattern: rootfs-*`、`merge-multiple: true`，把全部 artifact 摊平到 `dist/`。
3. `gen_rootfs_json.py --dist dist --out rootfs.json --repo <owner/repo> --version <tag> --build-date <build_date> --allow-partial`。
4. `write_notes.py` 生成 `notes.md`，同时 `cat` 进 `$GITHUB_STEP_SUMMARY`。
5. 发布：
   - `gh release view <tag>` 成功 → `gh release upload --clobber` + `gh release edit --notes-file --latest`（可重复运行同一 tag）；
   - 不存在 → `gh release create --title "NixOS rootfs <tag>" --notes-file --latest`。
6. 提交 `rootfs.json`：`git add` → 无 diff 则跳过 → `git commit`（`github-actions[bot]`）→ `git push`，失败则 `git pull --rebase` 重试，最多 3 次，仍失败即 `exit 1`。

**边界**：`release` 不再构建任何东西，也不改 `variants.json` / workflow。它对自己唯一的写操作是 `rootfs.json` 和 Release 资产。

## 3. 矩阵怎么生成

### 3.1 数据来源

`variants.json`（数组，一项一个变体）：

```json
{
  "id": "minimal",
  "name": "NixOS - Minimal",
  "file": "NixOS-Minimal",
  "distro": "NixOS",
  "description": "…",
  "output": "nixosRootfsTarballs",
  "attr": "minimal",
  "experimental": false
}
```

`systems.json`（对象，key 是 system）：

```json
{
  "aarch64-linux": { "arch": "aarch64", "runner": "ubuntu-24.04-arm" },
  "x86_64-linux":  { "arch": "x86_64",  "runner": "ubuntu-latest" }
}
```

### 3.2 笛卡尔积

`plan_build.py` 对每个 system 遍历每个 variant，摊成 `matrix.include` 的一行：

```text
for system in systems:
    for variant in variants:
        include: { system, arch, runner, variant_id, variant_name,
                   file, output, attr, experimental, attr_path }
```

`attr_path` 是拼出来的，格式固定：

```text
legacyPackages.<system>.<output>.<system>.<attr>
```

举例：system=`aarch64-linux`、output=`nixosRootfsTarballs`、attr=`minimal`

```text
legacyPackages.aarch64-linux.nixosRootfsTarballs.aarch64-linux.minimal
```

注意 `output` 后面**又出现一次 `<system>`**：这是 `nixosRootfsTarballs` 的约定形状（`nixosRootfsTarballs = { <system> = { <variant> = derivation; }; }`），不是笔误。

### 3.3 规模

| 变体数 | 架构数 | build job 数 |
|---|---|---|
| 2 | 2 | 4 |
| 2 | 1 | 2 |
| 5（历史表） | 2 | 10 |

`job_count` 会写进 plan 的 summary，点开 Actions 的 Plan job 就能看到。

### 3.4 变体增删的连带影响

新增一行 `variants.json` 会自动影响：

| 位置 | 影响 |
|---|---|
| `plan` 的 matrix | 新增格子，自动多跑对应 job |
| `rootfs.json` | `--lint` 的 `entries per release` 计数变化；发布时按新表收集条目 |
| Release notes | 表格多一行 |
| 文件命名 | 用新变体的 `file` 前缀 |
| 缓存 key | `hashFiles('systems.json','variants.json')` 变化，自动失效重建 |

不需要改任何 YAML 或 Python。

## 4. `--allow-partial` 的语义

### 4.1 默认行为（不带该标志）

`gen_rootfs_json.py` 按「system × variant」的完整笛卡尔积逐个去找

```text
dist/<file>-Droidspaces-rootfs-<arch>-<build_date>-<version>.tar.xz
```

任何一个缺失就 `fail`，并列出所有缺失文件名。这是本地使用的**默认安全姿势**：宁可报错，也不写出一个条目不全的索引。

### 4.2 带 `--allow-partial`

缺失的 tarball 只打 `warning` 到 stderr，仍然写出**只包含实际存在资产**的 `rootfs.json`。

流水线里 `release` 始终带这个标志，原因是：

- 用户可能只构建了一部分变体（`variants: minimal`），此时另外的变体本来就没有产物，不该报错；
- Release 的内容应当与「这次 run 实际产出的东西」严格一致，而不是与「表里声明的全部东西」一致。

### 4.3 它**不**代表什么

| 误解 | 实际 |
|---|---|
| 「允许构建失败」 | 不允许。`release` 依然是 `needs: [plan, build]`，有 build job 失败就不会进 release |
| 「允许发布空索引」 | 不允许。`entries` 为空时脚本直接 `fail("no tarballs found, refusing to write an empty rootfs.json")` |
| 「可以留残缺条目」 | 不会。缺失的条目根本不写，不会产生 `download_url` 指向不存在资产的条目 |

一句话：**`--allow-partial` 只是把「缺文件」从致命错误降级为警告，把索引范围从「声明全集」改成「实际产出集」。**

## 5. 缓存策略

### 5.1 分层

| 层 | 谁提供 | 缓存什么 | 生命周期 |
|---|---|---|---|
| Nix 二进制与配置 | `nix-installer-action` | 不含缓存，纯安装 | 每个 job |
| `/nix` 存储 | `nix-community/cache-nix-action@v6` | 已构建的 store path（闭包） | Actions cache，默认 7 天无访问淘汰 |
| workflow artifact | `upload-artifact@v4` | 最终 `.tar.xz` | `retention-days: 7` |

### 5.2 缓存 key 的设计

```yaml
primary-key: nix-<system>-<variant_id>-<hashFiles('systems.json','variants.json')>
restore-prefixes-first-match: |
  nix-<system>-<variant_id>-
  nix-<system>-
```

三级回退：

| 层级 | key 形状 | 命中情形 |
|---|---|---|
| 精确 | `nix-aarch64-linux-minimal-<hash>` | 同架构、同变体、表未变 —— 最快 |
| 同变体 | `nix-aarch64-linux-minimal-` | 表变了但变体没变，仍能命中大部分闭包 |
| 同架构 | `nix-aarch64-linux-` | 换了变体，但基础闭包（glibc、bash、systemd 依赖）大量复用 |

把 `systems.json` / `variants.json` 的哈希放进去的原因是：**表变了，构建内容就变了**，精确 key 必须失效；但不能让整个缓存失效，所以还保留宽前缀回退。

### 5.3 为什么要缓 `/nix`

NixOS tarball 的闭包包含 systemd、glibc、内核模块等，冷启动时要下载/构建上千个 store path，单 job 可能几十分钟到数小时。缓存的 `/nix` 直接把这些 path 落到本地，`nix build` 只剩下链接和打包。

注意：缓存的是**存储层**，不是「上一次的产物」。`nix build` 依然是真实的求值与构建，不会因为缓存跳过正确性检查（Nix 自身用哈希保证）。

### 5.4 artifact 与缓存的区别

| | cache-nix-action | upload-artifact |
|---|---|---|
| 内容 | `/nix` store 内部 path | `dist/*.tar.xz` 与校验文件 |
| 可见性 | 不面向用户 | run 页面可下载 |
| 用途 | 加速后续构建 | 交给 `release` job 汇总，也方便人工取用 |
| 保留 | 7 天无访问淘汰 | 固定 7 天（`retention-days`） |

## 6. 为什么用 commit sha 而不是分支名做 flake ref

`flake_ref` 接受分支、tag、commit sha 三种。正式发布**应当用 commit sha**（或至少是 tag），原因：

### 6.1 分支名是可变的

`flake_ref: main` 的含义是「构建时 `main` 指向的提交」。而 `main` 每天都在动：

- 今天构建的内容，明天用同样的输入重跑，得到的是**不同的系统**；
- Release 里写着「from `main`」，但没人能还原当时到底是哪个提交；
- 上游 `main` 已经出现过一次求值失败（`services.journald.settings`），如果流水线跟着分支跑，这种上游 breakage 会**无预警**地打进来。

### 6.2 commit sha 是不可变的

- 同一 sha → 同一份树 → 同一份求值结果；
- Release notes 里记录 sha，等于记录了可复现的构建输入；
- 出问题可以 `git checkout <sha>` 精确复现，而不是猜「当时 main 大概在哪」。

### 6.3 输入侧的额外保障

`plan_build.py` 会把 `flake_ref` 拼进 `flake_base`：

```text
flake_ref = main  →  github:owner/repo
flake_ref = <sha> →  github:owner/repo/<sha>
```

`main` 被特殊处理成「不加 ref」，因为 `github:` 前缀本身就默认分支。这个优化让默认值可用，但**不改变「默认值不适合正式发布」这个判断**。

### 6.4 tag 与 sha 的选择

| ref 类型 | 适用场景 | 风险 |
|---|---|---|
| 分支（`main`） | 冒烟测试、跟随上游最新 | 不可复现，随时被上游改动打破 |
| tag（`v1.2.3`） | 需要一个语义化标识 | 理论上 tag 可以被移动（实际上很少） |
| commit sha | 正式发布、需要复现 | 无（内容寻址） |

推荐做法：Release 用 sha；需要人能读懂的版本号时，在 Release 标题/notes 里附上 sha，而不是把 sha 当 tag 用。

## 7. 扩展点

### 7.1 加一个变体

只改 `variants.json`，见 [`使用指南.md`](使用指南.md) §5。前提是 flake 里已经有对应的 `output` + `attr`；没有就先在 `flake.nix` 里加输出。

### 7.2 加一个架构

在 `systems.json` 加一项 `"riscv64-linux": { "arch": "riscv64", "runner": "..." }`，同时确认：

- flake 里 `legacyPackages.riscv64-linux` 有该输出；
- 有可用的 GitHub runner 或自建 runner 标签（`runner` 字段直接用 GitHub 的 `runs-on` 值）；
- `gen_rootfs_json.py` 的文件名拼接用的是 `arch`，不需要改。

### 7.3 换一套 Linux 发行版

本流水线对「构建什么」是发行版中立的，只在两处有 NixOS 痕迹：

| 位置 | 痕迹 |
|---|---|
| `attr_path` 拼接 | 形式 `legacyPackages.<system>.<output>.<system>.<attr>`，其他 flake 若形状不同需要改 `plan_build.py` |
| `variants.json` 的 `distro` / `name` | 只是文本，改掉即可 |

`build` job 只认 `attr_path`，`release` job 只认文件名和 `rootfs.json` 的 schema，所以理论上换成别的发行版 tarball 只需要提供对应的 flake 输出（或把 `nix build` 换成别的构建命令）。

### 7.4 加可变字段

`gen_rootfs_json.py` 支持变体的 `extra` 对象：变体里写了 `"extra": {"foo": "bar"}`，生成的 `rootfs.json` 条目就会多一个 `"foo": "bar"`。适合带自定义元数据（例如最低内核版本、推荐内存）而不用改脚本。

## 8. 改流水线时的注意事项

| 事项 | 说明 |
|---|---|
| 不要退回 `find` 不带 `-L` | 见 §2.2.1，会重现「成功却报失败」 |
| 不要删 `fail-fast: false` | 否则一个坏变体会让整个 run 立刻取消，看不到其他格子状态 |
| 不要给 `release` 加 `continue-on-error` | 发布失败必须显式失败，否则会出现「Release 没创建但流水线绿」 |
| 改 `rootfs.json` schema 要同步 App | `rootfs.json` 是 App 与资产之间的契约，字段只加不改 |
| `rootfs.json` 不要手改 | 每次发布都会被脚本覆盖并提交，手改必然冲突 |
| 新增脚本只用标准库 | `gen_rootfs_json.py` / `plan_build.py` / `write_notes.py` 都只用 stdlib，runner 上不需要 `pip install`，本地也能裸跑 |
| 不要降低 `--accept-flake-config` 的必要性 | 部分 flake 依赖 `flakeConfig` 里的 `extra-substituters` 才能走缓存，去掉会显著变慢 |
