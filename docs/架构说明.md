# 架构说明（面向二次开发者）

> 上级索引：[README.md](../README.md)

## 1. 三个 job 的职责边界

流水线刻意切成三个阶段，而不是一个 build 包干，为了三件事：

| 目标 | 怎么实现 |
|---|---|
| 参数错误在 5 秒内暴露 | `plan` 先跑 `--lint`，表格有问题直接死，不浪费 runner |
| 单个变体挂掉不影响其他变体 | `build` 矩阵用 `fail-fast: false` |
| 构建与发布解耦 | `build` 只产生 artifact，`release` 才碰 API 和 git |

### plan 阶段

输入是 7 个 `workflow_dispatch` 参数；输出是 GitHub Actions outputs：
`tag`、`build_date`、`flake_base`、`matrix`（JSON 字符串）、以及三个计数。

`matrix` 直接以字符串形式输出，下游用 `fromJSON()` 展开。这样避免在 YAML 里写
嵌套表达式，也避免 `strategy.matrix` 只能静态写死的限制。

### build 阶段

一个矩阵项 = 一个 `(system, variant)` 对。runner 由 `systems.json` 的 `runner` 字段决定：

```json
{
  "aarch64-linux": { "arch": "aarch64", "runner": "ubuntu-24.04-arm" },
  "x86_64-linux":  { "arch": "x86_64",  "runner": "ubuntu-latest" }
}
```

注意这里是**原生 runner**，不是 QEMU 模拟。aarch64 用 ARM runner 直接跑，
速度与 qemu-user-static 差一个数量级。

### release 阶段

只有在 `publish == true` 时才执行。它做的事按顺序：

1. 下载所有 `rootfs-*` 前缀的 artifact，`merge-multiple: true` 展开到 `dist/`
2. 调 `gen_rootfs_json.py` 算 SHA256 与体积，重写 `rootfs.json`
3. 调 `write_notes.py` 生成 Release 说明
4. `gh release create`（已存在则 `upload --clobber` + `edit`）
5. git 提交 `rootfs.json`，push 失败就 rebase 重试 3 次

## 2. matrix 怎么生成

`plan_build.py` 是纯函数式的：读两个 JSON，算出一个笛卡尔积。

```
variants.json (2 条)  ×  systems.json (2 条)  =  4 个 job
```

如果关掉 `include_experimental`，先过滤 `experimental: true` 的变体，再算笛卡尔积。

每个矩阵项携带这些字段（全部原样传给 shell，不在 YAML 里重新拼）：

| 字段 | 用途 |
|---|---|
| `system` | Nix system，如 `aarch64-linux` |
| `arch` | 写进文件名的架构，如 `aarch64` |
| `runner` | GitHub runner 标签 |
| `variant_id` | 变体 id，用于 artifact 名 |
| `variant_name` | 中文名，仅展示用 |
| `file` | 文件名前缀 |
| `output` | flake 输出名，如 `nixosRootfsTarballs` |
| `attr` | 输出下的属性名，如 `minimal` |
| `experimental` | 布尔值 |
| `attr_path` | 拼好的完整属性路径 |

`attr_path` 公式：

```
legacyPackages.<system>.<output>.<attr>
```

注意是**单层 system**。上游 Droidspaces-OSS 用的是双层（`legacyPackages.<sys>.<output>.<sys>.<attr>`，
因为它在 `perSystem` 里又 `genAttrs systems` 了一遍）。本仓库的 flake 没有 `perSystem`，
只有一个 `genAttrs systems`，所以是单层。

## 3. `--allow-partial` 的语义

`gen_rootfs_json.py` 默认要求**所有**预期的 tarball 都存在，否则报错退出。
这能防住「构建漏了一个却没发现」。

但手动构建经常只跑子集（比如只测 `minimal`）。加了 `--allow-partial` 后，
缺的文件变成 warning，`rootfs.json` 正常写出，只是只包含本次真实构建的条目。

语义后果需要清楚：

| 场景 | 结果 |
|---|---|
| 全量构建（default） | `rootfs.json` 覆盖为完整 4 条 |
| 部分构建 + `--allow-partial` | `rootfs.json` 被覆盖为只有本次那几条 |
| 部分构建 + `publish=false` | `rootfs.json` 完全不变 |

所以只想试构建时，务必 `publish=false`，否则会把索引覆盖成残缺版本。

## 4. 缓存策略

`nix-community/cache-nix-action` 把整个 `/nix` 存进 GitHub Actions cache。

key 设计：

```
primary-key: nix-<system>-<variant>-<hash(systems.json, variants.json)>
restore-prefixes: nix-<system>-<variant>- , nix-<system>-
```

两级回退的含义：

1. 先用完全相同的 key（同变体、同表格内容）
2. 退到同变体的任意版本（表格改过但变体没变，大部分 store 路径仍然有效）
3. 再退到同架构的任意变体（`minimal` 和 `minimal-tools` 共享绝大部分闭包）

实测收益：第二次跑同一变体，`nix build` 从「下载整个闭包」变成「只构建 tarball 本身」，
时间从十分钟级降到一两分钟。

## 5. 为什么用 commit sha 而不是分支名

`plan_build.py` 在 `flake_repo` 为空时调用：

```python
f"github:{GITHUB_REPOSITORY}/{GITHUB_SHA}"
```

理由：

- **排队期间代码会变**。workflow 从触发到开始构建可能有几十秒，矩阵内 4 个 job 还不同时开始。
  如果用 `main`，早起的 job 拿到旧代码，晚起的拿到新代码，同一个 Release 里混了两种代码的产物。
- **flake 会重新求值**。`nix build github:owner/repo/main#...` 每次都可能解析到不同 commit，
  `flake.lock` 也完全不同，缓存直接失效。
- **可追溯**。产物名里虽不包 sha，但 Release 说明里记了本次 `GITHUB_SHA`，出问题能回到那个 commit 复现。

`flake_repo` / `flake_ref` 两个覆盖参数保留给「用别人的 flake 构建」的场景，例如临时测试上游修复。

## 6. 出错时的定位顺序

1. `plan` 挂了 → 看 `--lint` 输出，通常是 `variants.json` 字段缺失或重复
2. `build` 在 `Install Nix` 挂了 → 网络问题或 Determinate installer 版本问题，重跑
3. `build` 在 `nix build` 挂了 → 日志里找 `error:`，看是求值错误（选项不存在）还是构建错误（编译失败）
4. `build` 在 `Collect and rename` 挂了 → 日志会打印 `find -L ./result -maxdepth 3` 的完整目录树，
   通常意味着 attr_path 错了，或者 tarball 不在 `result/tarball/` 下
5. `release` 挂了 → 看是 `gh` 权限问题（`permissions: contents: write` 是否被组织策略覆盖）还是 `git push` 被保护分支挡住
